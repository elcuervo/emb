IV.The decision

A support email arrives; one command asks the original implementation's own five questions — which team, is it spam, is it phishing, how urgent, does it need a reply — and a single forward pass returns a decision sheet, not a vector.

Five answers, one call: a scripted model answers typed questions in a single forward pass, with calibrated confidence.

THE DECISION · 1 model · 5 questions · 1 forward pass · 0 input tokens · 32-dim sandbox miniature · the original's email preset

WHAT YOU ARE LOOKING AT

An inbox, a round of questions, one pass. The plate picks a support email, sends it with the five questions the original implementation ships for inbound email triage — Presets.email_questions, verbatim: a six-team category choice, an is_spam and is_phishing yes/no, a three-level urgency score, and a needs_reply yes/no — in one EMB.EVSHA, and draws the reply as a decision sheet: a distribution for the choice, a place on a ruler for the score, a split for each yes/no — every answer carrying its confidence.

What you're watching is the ONNX model: its typed head (the three question types it scores), the option markers it gathers from the sequence, the fitted temperature its calibration picks per question type and option count, its action head, and the single forward pass that answers all five at once.

Reading the confidence before you run it: on a choice or score, confidence 0.0000 is the undecided floor — every option equally likely, the most ambiguous possible answer; on a yes/no the floor is 0.5000 (a coin flip between yes and no); 1.0000 is fully decided. A triage-trained checkpoint spreads across this scale, and a real 0.0000 is the genuinely ambiguous email — the ticket a confidence threshold routes to a human.

The honesty bar: the sandbox runs a 32-hidden miniature of the Laya architecture, whose weights are random. It exercises the real mechanism — the sequence template, the five graph inputs, the calibration, the reply shapes — and its numbers are shapes, not judgments. The same command against the published checkpoints is the integration the end of this page shows.

WHAT JUST HAPPENED

One command carried the whole round: the email as KEYS, the five questions as ARGV[1], the checkpoint's budgets and temperatures as ARGV[2]. The preset built one sequence per question — [CLS] … [SEP] [MASK] option [SEP] state [SEP] — gathered every option's marker into one batch, and the model scored them all in a single pass.

The five rows appear together because they came back together: one reply, one decision sheet. Each row is the model's own tempered probabilities — a choice row draws them as bars, a score row as a position on its legend, a yes/no row as a split — rounded the way the calibration contract says, with the action probability in the sheet's head.

WHY IT MATTERS

A classifier zoo is a pipeline: one model per label set, glued together, impossible to keep calibrated. A decision model is one checkpoint and one call — the questions are data, so the app's question set lives in the repo, diffs in review, and the whole triage is one round trip from a Redis client you already have.

The sheet's confidence is the model's own calibration: a question type and option count pick a fitted temperature, and the answer reports how decided the distribution is. Nothing hallucinates a label wholesale — every option is scored.

THE EXACT COMMANDS

The exact call the plate just made — the state, the original's Presets.email_questions verbatim, the miniature's calibration envelope. Point the same three arguments at a published checkpoint and the command is the production integration.
