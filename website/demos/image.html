III.The image

A picture into the same space as a sentence. One model, two modalities, so an image can be matched against words it never saw as a caption.

FIG. 9 — THE IMAGE · CLIP ViT-B/32 · 512 dimensions · 8 labels · one shared space

WHAT YOU ARE LOOKING AT

CLIP was trained so that an image and its caption land near each other. That makes one space hold two kinds of thing — a photograph and a phrase are both points, and the distance between them is a number you can sort.

So the labels below are not trained: they are text, embedded beside the image and ranked. Pick a different sample and the ranking moves. That is zero-shot classification, and it is the same cosine the first plates used. The six samples are public-domain paintings and photographs, committed with the gallery.

WHAT JUST HAPPENED

The browser downscaled the sample to 512 pixels and base64-encoded it, because JSON cannot carry bytes; the bridge decoded it back to bytes and passed them to the sandbox. The server preprocessed them to the model's own pixel_values tensor, ran the fused CLIP graph once for the image and once for each label, and returned the softmax of the cosines.

There is no upload: the samples ship with the page and are used for this request only. The bridge accepts binary only for this one preloaded script, only for the vision model, and only within its image bounds — a text command cannot carry an image, and a larger one is refused before decode.

WHY IT MATTERS

One model for two modalities is how image search, tagging, and content moderation work without a classifier per label: embed everything once and compare. A new label is new text, not a new training run.

It is also the strongest argument for the scripting layer. The fused graph needs both branches' inputs for either run; the script builds the unused branch as a constant tensor host-side, asks the graph for one output per run, and reduces packed float32 with emb.math — no 150,000-element Lua table, one round trip.

THE EXACT COMMANDS

One scripted command. The count is the number of keys — the image is the only one; the labels are arguments. The bridge carries the image as base64 in the argument named by bin. 

EMB.EVSHA clip <zeroshot.lua sha1> 1 <image bytes> raven storm …
# -> { label = "raven", score = 0.31, probs = {...}, scores = {...} }

# the bridge request: bin names argument 4 as base64 bytes
{ "args": ["EMB.EVSHA", "clip", "<sha>", "1", "<b64>", "raven", …], "bin": [4] }
