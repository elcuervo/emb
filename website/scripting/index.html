Scripting

The plain pipeline is model(input) → output. A script rewrites the edges around that same call in Lua — model(fn(input)) → output — so a raw-logits model can answer as a labelled classifier, or a cross-encoder can answer with a score. This page is the complete reference for the scripting engine: the commands, the sandbox it runs in, every host function, the tensor and reply forms, the budgets, and the cache identity.

Pre-1.0. emb is at v0.4.3.pre4 and interfaces may still move. emb has one version: the scripting surface reports it as emb.API_VERSION, and the same value is folded into every reply-cache key, so an upgrade never serves a reply computed under an older surface.

Everything the scripting engine is: the commands, the sandbox, the emb.* host API, tensors, replies, budgets and cache identity.

01 · The script surface

A script is evaluated once per request, in a fresh sandboxed Lua state. The request's texts arrive positionally in KEYS and the command's remaining arguments in ARGV, exactly as Redis exposes them. The script's return value is converted to RESP and sent as the reply. The wrapper also passes KEYS and ARGV as function arguments, so an explicit function(KEYS, ARGV) signature works too.

A single-text request returns the script's value itself. A multi-text request runs the script once with every text in KEYS, and the script must return one value per text — an array whose elements correspond 1:1 to the texts, in order. A multi-text result that is not such an array is an error reply.

Scripts are pure compute. Identical inputs always produce identical replies, which is what makes a reply cacheable and a deployment reproducible. See 04 · The sandbox for exactly what is removed to guarantee it.

02 · Commands

Scripts are cached per model, keyed by the SHA1 of their bytes. EMB.EVAL sends the source inline; EMB.EVSHA calls a cached script by its digest. The model must already be mounted in config — scripts and arguments never require a config change.

EMB.EVAL <model> <script> <numtexts> <text...> <arg...>
Compile and run an inline script against the model. The numtexts texts become KEYS; the remaining arguments become ARGV. A numtexts that does not match the actual number of text arguments is a wrong-arity error, and nothing executes.
EMB.EVSHA <model> <sha> <numtexts> <text...> <arg...>
Run a script already cached for the model, by SHA1, with the same KEYS/ARGV semantics as EMB.EVAL. An unknown digest is a no-such-script error.
EMB.SCRIPT LOAD <model> <script>
Compile and cache the script (rejecting a script that does not compile), and reply with its SHA1. Scripts can also be preloaded at boot from config.
EMB.SCRIPT EXISTS <model> <sha...>
One 1/0 per digest, in order, for the model's cache.
EMB.SCRIPT FLUSH [<model>]
Drop the model's cached scripts, or every model's when the model is omitted. The compiled-prototype cache is dropped with it.

Capability is detected, not refused. When a model cannot produce embeddings, emb.embed is absent rather than an error at call time, so a script can branch on type(emb.embed). The same gating applies to the image block. The server never refuses to evaluate a script on version grounds.

03 · Preloading from config

A model entry can name script files to load at boot, so EMB.EVSHA works without a client-side EMB.SCRIPT LOAD round-trip. An entry is either a string naming a source file, or a mapping with a required path and an optional config. Relative paths resolve against the directory holding the config file.

The mapping's config is exposed to that script alone as emb.script.config — a Lua table of the same shape json.decode produces, and an empty table when the entry declares none, so emb.script.config.x or fallback reads the fallback. The server never interprets a key; it validates only that the config is a mapping. The config participates in the script's reply-cache identity, so editing it invalidates replies computed under the old one.

Preload is validated, not trusted. At boot each path must name a readable regular file, the source must fit the size cap, and the script must compile; a missing file, an oversized script, invalid Lua, or a malformed config is fatal and prevents startup, naming the path. Each valid script is cached by SHA1 and its compiled prototype is cached so the first EMB.EVSHA skips the compile step.

04 · The sandbox

Every evaluation runs in a fresh Lua state with only a curated subset of the standard library open. Anything with hidden state, I/O, or an external loader is removed after the libraries are opened, and each invocation gets a new state, so no global leaks between evaluations and a runaway script kills only its own request.

os · io · debug
The clock, the filesystem, and the debug hooks are unavailable.
load · dofile · loadfile · module · require
There is no loader and no module system; a script is self-contained.
channel · coroutine
Concurrency primitives and cooperative scheduling are unavailable.
math.random · math.randomseed
Randomness is unavailable, so a reply is a pure function of its inputs.

What remains is the deterministic core — strings, tables, the numeric library, pattern matching — plus the host surface documented below. The result is a script whose reply depends only on its source, its KEYS/ARGV, its config, and the model, which is exactly what the reply cache relies on.

Resources open lazily. A script that returns a constant allocates nothing: named-tensor sessions and the tokenizer are created on the first emb.run, emb.run_batch, or emb.tokenize.* call, and image resources on the first emb.image.* call. Named-tensor sessions are a separate pool from the embedding path, sized by the model's script_workers (unset or 0 auto-tunes, bounded by the embedding pool's own session count), so scripting never adds more model instances than the embedding path already committed to.

05 · The host API

These are the only host functions a script can reach. Everything else is the standard library subset described above. Arguments shown in brackets are optional; functions marked unavailable for a model are absent rather than raising, so type() detects them.

Inference

emb.run(inputs [, opts])
One inference over named tensors. Returns the graph's named outputs — {name = {shape, data, dtype}} — as a first value and the model call's duration in milliseconds as a second. opts accepts {bytes = true} for packed outputs and {outputs = {name, …}} to materialize only the named graph outputs.
emb.run_batch(items [, opts])
An array of input-spec tables, each {name = {shape, …}}, merged into one padded inference run and returned as an array of per-item output maps, plus the call's duration. All items must declare the same tensor names, ranks, and dtypes; padding extends each tensor to the batch maximum, zero-filled, and masking semantics stay the script's responsibility. For graphs whose output depends on batch composition, each item runs on its own.
emb.embed(text | {text, …}[, {bytes = true}])
Pooled, normalized embeddings through the same path the EMB command uses — same pool, same batcher, same cache — so a text embedded here and by EMB shares one cache entry. A string yields one vector, an array yields one per text, and {bytes = true} returns packed little-endian float32 instead of per-element arrays.

Similarity and distance

emb.similarity(a, b [, metric])
Higher is more similar. Metrics: cosine (default), dot. Both operands may be a per-element array or a packed float32 string and must have equal length.
emb.distance(a, b [, metric])
Lower is closer. Metrics: l2 (default), l2sq, cosine (as 1 − cosine).

Tokenization

emb.tokenize.encode(text, max_len)
The model tokenizer's own pipeline, returning {ids, mask, offsets} with per-token byte offsets.
emb.tokenize.encode_pair(first, second, max_len)
The BERT-family pair template, returning {ids, mask, offsets, sep}, with the separator position for the two segments.
emb.tokenize.encode_plain(text, max_len)
Like encode but with no special tokens, returning {ids}. Useful for building a model's template yourself.
emb.tokenize.words(text)
A generic word split following BertPreTokenizer rules, returning {words, starts, ends} with byte offsets.
emb.tokenize.pretokenized(words, max_len)
Encode an already-split word list, returning {ids, word_ids} — the id of the word each token came from.
emb.tokenize.special_ids()
The model's special token ids: {mask, cls, sep, pad, mask_token}.

Images

emb.image.preprocess(bytes)
Decode raw image bytes and apply the model's configured preprocessing (size, crop, resample, rescale, mean, std), returning a tensor spec {shape = {1, 3, H, W}, bytes = <float32>, dtype = "f32", input = <tensor name>} that emb.run accepts with no per-element Lua table. Preprocessing is deterministic and bounded by the same byte and pixel caps as EMB.IMG.
emb.image.info()
The model's configured preprocessing plan: {input, size, crop, resample, rescale, mean, std}.
emb.image.embed(bytes | {bytes, …})
Pooled, normalized image embeddings for raw encoded image bytes, in the model's shared text/image space. Shares the same image cache and resources as EMB.IMG, so an image embedded by either path is a hit for the other.

Vector math

emb.math.sigmoid(x) · emb.math.softmax(v) · emb.math.argmax(v)
Element-wise primitives. Each accepts a per-element array or a packed float32 string and is vectorized per array; a scalar returns a scalar. softmax is numerically stable and argmax returns the 1-based index and its value.
emb.math.float32_bytes(v)
Pack numbers into one little-endian float32 bulk — unpack('e*') on the client — byte-compatible with the bytes tensor field.
emb.math.dot(a, b) · emb.math.cosine(a, b) · emb.math.l2(a, b)
Pairwise inner product, cosine similarity, and Euclidean distance over two operands of equal element count.
emb.math.norm(a)
The L2 norm. dot, l2, and norm define the empty operand as 0; cosine errors on it, because its denominator is zero.
emb.math.mean_pool(hidden, shape, mask)
Masked mean over a {batch, seq, dim} hidden tensor, ignoring masked positions.
emb.math.cls(hidden, shape)
The first sequence position's vector — the CLS representation.
emb.math.topk(values, k)
The k largest values as {index, value} entries, descending, 1-based indices, stable on ties.
emb.math.gather(values, indices)
values[indices[i]] for each index — sparse lookups without a Lua loop.
emb.math.slice(tensor, shape, offset, length)
A contiguous span of a shaped tensor.
emb.math.scale(values, factor) · emb.math.add(a, b)
Element-wise product by a scalar, and element-wise sum of two equal-length operands.

JSON and the script's own facts

json.encode(value) · json.decode(raw)
Structured replies and parsing. A decoded JSON object becomes a string-keyed Lua table.
json.decode_ordered(raw)
Like json.decode, except each JSON object becomes an array of {k = <key>, v = <value>} pairs in document order, with a trailing n = <count> sentinel; arrays decode as plain integer-keyed tables. Use this when object key order is load-bearing, because a plain Lua table cannot hold nil and string-key iteration is not deterministic in the sandbox VM.
json.null
The null sentinel, so null round-trips inside arrays.
emb.script.config
The running script's own declared config, from the preload entry. An empty table when none was declared; semantically opaque to the server.
emb.API_VERSION
The server's version, as a string — the same value INFO reports as emb_version. It is folded into reply-cache identity, so an upgrade never replays a reply computed under an older host surface.

Prefer emb.embed for embeddings and scoring. It is pooled, normalized, cached, and shares the server's batcher and sessions with EMB. For a large graph output, request {bytes = true} and reduce it with emb.math.* rather than indexing element-by-element — a packed buffer crosses into the host once and the reduction runs in Go, not Lua.

06 · Tensors and replies

An input spec is a named tensor with exactly one of data, fill, or bytes. Every output carries its dtype, so a returned tensor is already a valid input spec and no dtype is re-inferred from element values — an all-integral float32 output would otherwise be mistaken for i64.

{shape = {…}, data = {…}, dtype?}
A per-element array. Integral numbers infer i64 unless a dtype is given.
{shape = {…}, fill = n, dtype?}
A constant tensor built host-side: every element equals n, allocated by the server with no Lua data table. A fractional fill infers f32.
{shape = {…}, bytes = <string>, dtype}
Raw little-endian elements. dtype is required — there is no inference from content — and the byte length must equal elements × width exactly. This is where a packed output or an emb.math.float32_bytes buffer goes back in.
dtype
"f32" (4 bytes), "i64" (8 bytes), or "b1" (1 byte). A packed tensor round-trips with the shape it was returned with, so a dtype never needs re-inferring.

The reply grammar

The script's return value converts to RESP2 by a fixed grammar. Keys are converted in sorted order, so identical tables always produce identical bytes — the content-addressed reply cache depends on it.

string
A bulk string. Byte-safe: UTF-8, JSON, and arbitrary binary all pass through.
number (integral) · number (fractional)
An integral number is an integer reply; a fractional number is a bulk string, because RESP2 has no double — the decimal is not truncated.
true · nil · false
true is the integer 1; nil and false are a null reply.
list table (keys 1…n)
An array reply, converted recursively. An empty table is an empty array.
string-keyed table
A flat field/value pair array — the HGETALL shape — sorted by key. Values nest: a hash value may itself be an array, hash, bulk, integer, or null.
{err = "message"}
An error reply. A message containing CR or LF is rejected rather than written, so an error can never splice a second RESP frame onto the wire.

Mixed keys are an error. A table whose keys are some integers and some strings has no unambiguous reply form and is rejected at conversion. Use an array for a sequence and a string-keyed table for a record, never both in one table.

07 · Budgets

Every cap below is enforced before the allocation it bounds, so a pathological script fails with an error instead of exhausting the server. The tensor caps are charged across the whole evaluation: data, fill, and merged batch tensors, plus every materialized output, draw on one budget, so a loop of individually valid calls cannot sidestep the total.

64 KiB — script source
The maximum script size, checked before compilation. Both EMB.SCRIPT LOAD and boot preloading use it, and an oversized script is script exceeds size limit.
30 s — evaluation deadline
Wall-clock bound on one evaluation. Scripts are pure compute, so a real workload finishes in microseconds; exceeding it is script deadline exceeded.
16,777,216 elements — one tensor
The per-tensor element cap, applied to a fill or a packed input before the host allocates it (≈64 MiB at 4 bytes per element).
67,108,864 elements — one evaluation
The total tensor-element budget shared by every emb.run and emb.run_batch call in one evaluation (≈256 MiB at 4 bytes per element), including merged batch tensors and every materialized output.
256 MiB — one output tensor
The byte cap on a single materialized output. Packed and per-element forms both materialize the whole tensor, so the cap applies to either.
256 bytes — cache-key tail
An input text at or below this length is inlined into the reply-cache key; a longer one becomes a SHA-256 digest instead, so one key cannot retain megabytes.
1,024 — compiled prototypes per model
The bound on the per-model compiled-script cache, so EMB.EVAL with unbounded unique inline scripts cannot grow it without limit.

Outputs are metered too. A materialized output is charged against the evaluation's element budget exactly like an input, so the packed form cannot be used as a way around the total. What the budget does not bound is the model's own inference cost — only the scripting side's allocation.

08 · Caching and identity

Scripts are cached per model by the SHA1 of their source bytes — Redis's own script digest. The compiled-prototype cache is separate and keyed by (model, wrapped source), so a repeat EMB.EVSHA skips parsing and compiling while still instantiating a fresh sandboxed state for every evaluation.

Scripted replies are content-addressed under a second key, built so that two different requests cannot collide and a changed surface cannot serve a stale value:

Four things are folded in deliberately. The server version (emb.API_VERSION) means an upgrade never replays a reply computed under an older host surface. The config digest means editing a preloaded script's config misses rather than serving the old answer. The text count keeps the single-text namespace (the script's value itself) apart from the multi-text one (one element per text). And the representation byte separates a short literal input from the digest of a long one, so a short text equal to #<sha256> cannot alias a long payload's reply.

The cache is per text. A multi-text request is a hit only when every text is; a miss re-evaluates once with all texts in KEYS, so the script always sees the true request context. A request with a repeated text is not cacheable, because the per-text reply would be ambiguous. When caching is off, the script runs and the reply is computed directly.

Because the server version is one of the folded fields, cached replies do not survive an upgrade — a restored snapshot warms only the keys matching the running version. That is the intended trade of a single version: correctness over warmth.
