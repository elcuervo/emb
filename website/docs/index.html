Documentation

emb is a simple yet powerful self-hosted inference server that speaks the Redis protocol. It implements the protocol rather than shipping a client, so the Redis client you already have is the SDK. This page is the reference: everything below is the behaviour of the shipped server, and the repository README remains the source of truth.

Pre-1.0. emb is at v0.4.3 and interfaces may still move. Commands, configuration keys and reply shapes on this page describe that version.

Everything the server does, as commands and replies. Each section shows the exact command and what comes back.

01 · Install and first vector

Three ways to get the server. All of them install the same single binary with ONNX Runtime embedded — inference, batching, caching, scripting and operations are server-side, so there is nothing to run alongside it.

Start it with a model. The server auto-downloads from Hugging Face when given a repository id, and auto-detects the embedding dimension, maximum length, output tensor and pooling strategy from the ONNX graph and config.json.

platforms
macOS on Apple Silicon; Linux on amd64 and arm64.
default port
:6379 — the Redis port, so existing tooling needs no new mental model.
config
a YAML file via -config, or the same settings as inline flags. See Configuration.
model source
a local ONNX path, or a Hugging Face repository id that is downloaded and cached.

02 · Commands

The command surface. Argument shapes are shown in full: where a command takes a reply-format keyword, its position is fixed and is described under Replies and protocol.

EMB <model> [BLOB|VALUES] <text> [text…]
Embed one or more texts. With BLOB (the default), one text returns a bulk string and several return an array of bulk strings of float32 bytes. With VALUES, a dtype/shape/values envelope with decimal values.
EMB.MULTI [BLOB|VALUES] <model> <text> [<model> <text>…]
Embed texts across different models in one round trip. Each reply is the vector for its model; a failed pair returns null in its own slot without failing the call. Under VALUES each envelope also carries its model key, since per-pair dimensions differ.
EMB.MODELS
List the loaded models with their dimensions and status.
EMB.INFO <model>
Model details: dimension, workers, requests served, average latency, batch determinism, the CPU share, thread width and spinning the process granted this model, the embedding path's dispatch, admission and run timings and runs (embed_dispatch_wait_us, embed_admission_wait_us, embed_run_us, embed_runs), and that model's own cache counters — cache_hits, cache_misses, cache_hit_rate, cache_evictions, cache_entries, cache_max_bytes.
EMB.STATS
Server statistics: uptime, total requests, live connections, active requests, a per-model breakdown, and process resources — RSS in MB, CPU user/system microseconds, goroutines.
MONITOR [seq] [limit]
Recent completed-request events from a bounded ring of up to 8192: sequence, timestamp in µs, model, text count, latency in µs, error, then the request's own attribution — cached_texts (how many of its texts the reply cache answered), attributed (whether the server measured its phases at all), and dispatch_us, admit_us, run_us: the time its uncached texts spent waiting for a session or batch window, at the process CPU gate, and running. They follow err, so a client reading the original six positionally is unaffected. Pass the last seq you saw to fetch only newer events. Request texts are never included.
EMB.READY
Health check. +OK when ready, otherwise -ERR with a reason: loading, draining, no models.
EMB.EVAL <model> <script> <numtexts> <text…> <arg…>
Evaluate a Lua script once against a model, with KEYS = texts and ARGV = args.
EMB.EVSHA <model> <sha> <numtexts> <text…> <arg…>
Evaluate a cached script by SHA.
EMB.SCRIPT LOAD <model> <script>
Compile, cache and return the script's SHA1.
EMB.SCRIPT EXISTS <model> <sha…>
Which of the given scripts are cached: 1 or 0 per SHA.
EMB.SCRIPT FLUSH [<model>]
Clear cached scripts; all models when the model is omitted.
EMB.CACHE.FLUSH [model]
Remove all cached embeddings, or only the entries for one model. Returns the removed count.
EMB.SAVE
Accept an asynchronous cache snapshot. Poll EMB.STATS or INFO cache for completion or failure.
EMB.HELP
The command reference, including the full script surface.
INFO [section…]
Redis-style INFO with sections server, cache, keyspace, stats, memory, cpu, clients. Stays a bulk string under both protocol versions, as in Redis.
CONFIG GET [glob] / CONFIG SET
Read or live-tune runtime settings. Both require authentication.
AUTH <password>
Authenticate the connection. Required when password is set.
HELLO [2|3]
Negotiate the RESP protocol version for the connection; the default is 2. Bare HELLO reports the current version.
PING
PONG.

03 · Replies and protocol

EMB and EMB.MULTI accept an optional leading reply-format keyword. BLOB is the default: raw little-endian float32 bytes as a bulk string. VALUES returns a self-describing envelope for clients, tooling and debugging that cannot decode raw float32 bytes.

Where the keyword is read

The keyword is detected only at its fixed position — right after the model name, or before the pairs in EMB.MULTI — and is never scanned from the tail of the text. A trailing word that happens to read BLOB or VALUES embeds normally. The one collision is a first text in a multi-text call: EMB m VALUES hello treats VALUES as the keyword, so write it twice — EMB m VALUES VALUES hello — or reorder the texts. As a safety measure both words are reserved and cannot be used as model names.

RESP2 by default, RESP3 on request

Connections speak RESP2. A client upgrades with HELLO 3 and can go back with HELLO 2. Under RESP3 the VALUES numbers arrive as typed doubles instead of decimal bulk strings, and EMB.INFO, EMB.STATS, EMB.MODELS and CONFIG GET reply with maps instead of flat key/value arrays. Nulls encode as _ rather than $-1. INFO stays a bulk string in both, and errors stay simple errors.

04 · Configuration

Settings live in a YAML file passed with -config, or as the equivalent inline flags. Model names are declared here; a model's layout is decided lazily on first use unless it is marked to preload, and the first requests after a cold start are refused with ERR not ready while it lays out in the background.

Model options

onnx / tokenizer
A local ONNX path and tokenizer file, or repo to download both from Hugging Face.
normalize
Default false. L2-normalizes the output.
output_tensor
Auto-detected from the graph when omitted.
preload
Default false. Decide the layout at startup instead of on first use; a lazy model refuses the first requests after a cold start with ERR not ready while it lays out in the background.
pad_output
Default false. Pads sequences to max_length with trailing zeros, for legacy implementations that do not pass an attention mask.
workers
Auto-tuned. Number of worker goroutines.
intra_op_threads
Defaults to cores−2 under cpu_budget: off; with the default cpu_budget: auto the process budget and calibration choose it. Set it explicitly to override — an explicit value is never replaced.
scripts
Default []. Lua scripts to preload at boot; relative paths resolve against the config file's directory. An invalid script — bad syntax, missing file, oversized — fails startup.
batching
Default {timeout: 1, max_batch: 32, max_batch_tokens: 16384}.
script_callers_per_session
Default 4. How many scripted evaluations may share one named-tensor session at once; the runtime controller adapts within it.
capacity
Default auto. The creation-time layout: auto keeps the derived layout and adapts at runtime, latency pins spinning on with one caller per session, throughput pins shared sessions with spinning off.
autotune
Default auto. auto/callers run the concurrency controller; off fixes concurrency at the configured value.

Adaptive capacity

Scripted models are shared: several evaluations run at once on one named-tensor session, up to script_callers_per_session. Out of the box the server observes each model's traffic shape and moves the effective allowance inside that cap — shrinking under sustained serial traffic and re-expanding to the cap on the first burst — so neither an unusually serial nor an unusually bursty workload needs a hand-picked layout.

auto (default)
The derived layout, with the controller active; the allowance tracks the observed traffic class.
latency
Pinned for round trips: ORT spinning on, one caller per session, controller off.
throughput
Pinned for concurrency: shared sessions with spinning off, allowance at the cap, controller active.

A profile picks a default; an explicit setting wins. An explicit allow_spinning is kept, and autotune: off pins the allowance at the configured value even under capacity: throughput. A model whose class stays saturated is CPU-bound — more concurrency cannot help — so the controller holds the allowance and logs one recommendation to raise script_workers or intra_op_threads instead.

Process CPU budget

Embedding and image models are budgeted as one process. Out of the box the server detects the CPU allowance it may use, holds back cpu_reserve, and calibrates each model's session count and intra-op width inside what is left — so a default deployment sizes itself to the machine instead of to a hard-coded thread count.

cpu_budget
Default auto. auto derives the admitted budget from the detected allowance minus cpu_reserve; off disables the budget and restores the legacy width rule (intra_op_threads defaults to cores−2); a positive integer pins the budget directly.
cpu_reserve
Default 2. CPUs held back from the budget for tokenization, request parsing and dispatch. Only valid with cpu_budget: auto.
calibrate
Default true. Runs startup trials to pick each model's session count and width within the admitted budget.
weight (per model)
Default 1. A model's relative share of the budget when several are loaded, so a heavier model gets more of the admitted tokens.

Precedence: an explicit workers or intra_op_threads is never replaced — the plan reports the width you asked for. cpu_budget: off is the kill switch and restores the legacy width rule exactly. The budget bounds admitted intra-op work, not physical CPU: tokenization and Go work sit outside it, and shared embedding and image sessions do not spin under the automatic policy.

Batching

Smart batching is on by default for every model: a 1 ms window coalesces concurrent requests into shared ONNX runs, bounded by a token budget. With batching on, tokenize_workers defaults to min(4, cores) and tokenization runs concurrently with inference. Set timeout: 0 to fall back to the worker pool.

Caching

An in-process LRU keyed by model:text, sized in bytes, as a percentage of RAM, or auto (roughly 13% of total RAM). CONFIG SET cache 1GB resizes it live and evicts immediately. Cache statistics appear per model in EMB.INFO and as a section in INFO.

Persistent cache snapshots

Snapshots optionally preserve the in-process LRU across restarts, so a cold start warms in seconds instead of re-inferring. They are operationally inspired by Redis RDB but are a small emb-specific streaming format and are not RDB-compatible. Persistence is completely dormant while cache_file is empty.

A snapshot contains the original input text and the embedding bytes. Treat the file as sensitive, and treat it as a warm-start optimization rather than a durable database — it is disposable, and a restore that does not fit the configured budget is simply skipped.

05 · Lua scripting

This section is the introduction. The scripting reference carries the complete host surface — every emb.* function, the tensor and reply forms, the budgets, and the reply-cache identity.

The plain embed command is a fixed pipeline: model(input) → output. A script replaces the edges around that same call with your own code — preprocessing, postprocessing, and the reply itself — so a raw-logits text model can answer as a labelled classifier, or a cross-encoder can answer with a score.

Loading and calling

The script surface

Scripts read texts from KEYS and arguments from ARGV. A multi-text call runs one evaluation with KEYS holding all texts, and requires one returned value per text.

emb.run({name = {shape, data|fill, dtype?}, …})
Named-tensor inference, returning {name = {shape, data}} per output and, as a second value, the model call's duration in milliseconds.
emb.run_batch({item, …})
One model call for N items, padded into a single session run; its second return value is that call's duration in milliseconds.
emb.tokenize.encode(text, max_len)
The model tokenizer's own pipeline, returning {ids, mask, offsets}.
emb.tokenize.encode_pair(a, b, max_len)
BERT-family pair framing, returning {ids, mask, offsets, sep}.
emb.tokenize.words(text)
Generic word split following BertPreTokenizer rules, with byte offsets.
emb.tokenize.pretokenized(words, max_len)
Encode an already-split word list, returning {ids, word_ids}.
emb.math.{sigmoid, softmax, argmax}
Post-processing primitives, vectorized per array.
emb.math.float32_bytes(vals)
Pack numbers into one little-endian float32 bulk — unpack('e*') on the client.
json.{encode, decode}
Structured replies and parsing.

An input spec is {shape = {…}, data = {…}, dtype?}, or {shape = {…}, fill = n, dtype?} to build a constant tensor host-side: every element equals n, allocated by the server with no Lua data table round-trip. fill and data are mutually exclusive; an explicit dtype ("f32" / "i64") wins, and a fractional fill infers f32. Replies convert through a fixed grammar: a Lua string becomes a bulk, a list an array, a string-keyed table a flat hash, and {err = "…"} an error reply.

Scripts are pure compute. os, io, require and loaders, coroutines and math.random* are stripped, so identical inputs always produce identical replies.

Reference script and snippets

Scripts live in two places: examples/scripts/reference/ holds maintained implementations exercised by CI, and examples/scripts/snippets/ holds illustrative patterns.

reference/gliner2.lua
Span extraction against supplied labels — the maintained reference. Reads its logits in packed form and decodes with emb.math.gather + emb.math.sigmoid.
snippets/sst2.lua
Text classification with a softmax over logits, returning a label and a confidence.
snippets/qa.lua
Extractive question answering over a context.
snippets/rerank.lua
Cross-encoder reranking, returning sigmoid scores.
snippets/siglip2.lua
Text embedding on a fused CLIP export (see the note below).
snippets/image_zeroshot.lua
Cross-modal zero-shot classification with emb.image.preprocess.

For embeddings and scoring, prefer emb.embed (pooled, normalized, cached, and sharing the server's batcher and sessions with EMB) and the similarity methods — emb.similarity(a, b [, metric]) for higher is more similar (cosine, dot) and emb.distance(a, b [, metric]) for lower is closer (l2, l2sq, cosine). Both accept arrays or packed float32 strings. Large graph outputs should be requested with {bytes = true} and reduced with emb.math.* rather than indexed element-by-element.

siglip2 is the text branch only. The script runs onnx-community/siglip2-base-patch16-224-ONNX's fused export, whose image branch is not populated by a text request: it feeds pixel_values as a constant zeroed 1×3×224×224 tensor and reads text_embeds (768 floats), which depend only on the text tokens. For a real image path use emb.image.preprocess (see examples/scripts/snippets/image_zeroshot.lua) or emb.image.embed, which returns a pooled image embedding in the model's shared text/image space.

06 · Operations

Health checks

EMB.READY answers +OK when the server can serve traffic, or -ERR with a reason — loading, draining, no models. Point a load balancer's TCP health check at it; the Ruby client exposes the same probe as ready? and ready.

Connection lifecycle

Three knobs bound the connection and request surface. idle_timeout defaults to 15 minutes and reaps connections that stop sending commands; pooled clients reconnect transparently, a long-idle interactive session is closed and must reconnect. max_connections refuses connections at the cap, closing the socket immediately without counting it. max_concurrent_requests answers EMB and EMB.MULTI with ERR busy … at the cap, giving consumers backpressure instead of unbounded queueing — while PING, AUTH, EMB.READY, EMB.STATS, EMB.MODELS, EMB.INFO and EMB.HELP still answer, so ops can probe a saturated server. Both caps default to 0 (unlimited).

Observability

EMB.STATS reports uptime, total requests, live connections and the real in-flight active_requests count, a per-model breakdown, process resources (mem as RSS in MB, CPU user and system microseconds, goroutines), the cache counters, and the effective limits — enough to classify an incident as volume, saturation, or churn, and to confirm RSS and goroutines are flat between polls.

INFO [section…] renders Redis-format sections:

server
redis_version, emb_version, uptime_secs, process_id.
cache
Hits, misses, hit rate, evictions, entries and byte usage.
keyspace
Per-model db0:model=…,keys=…,hits=…,misses=…,hit_rate=….
stats
total_requests, total_tokens, total_errors, models_loaded, and network bytes in both directions.
memory
used_memory_rss_bytes including ONNX and CGo, heap bytes, goroutines, total system memory.
cpu
User and system microseconds, gomaxprocs.
clients
active_requests.

CONFIG GET [glob] reads the live registry (CONFIG GET cache*) and CONFIG SET tunes it at runtime, including live cache resizing — CONFIG SET cache 1GB evicts immediately — and swapping the password, which affects new connections only. Read-only parameters such as the listen address, TLS and models are reported by GET and rejected by SET. Both require authentication, matching Redis.

Autotune state

EMB.INFO <model> reports the script path's live capacity state, so an operator can tell queueing from compute without guessing:

script_traffic_class
idle, latency, throughput, or saturated — the class of the most recent sampling window.
script_inflight
Evaluations running right now, counted at the inference boundary; cache hits never reach it.
script_concurrency_current
The effective per-session allowance the controller is using.
script_concurrency_target
The configured cap, script_callers_per_session.
script_autotune_active
1 while the controller is adapting, 0 when it is fixed.

latency with inflight at the session count is the serial case; throughput with inflight above it is a burst; saturated means the process is CPU-bound and the allowance is held. The kill switch is autotune: off, which pins the allowance at the configured value for the process lifetime.

Process CPU plan

The startup log and EMB.STATS report the plan the server settled on, so the layout is observable rather than implied:

cpu_allowance
The CPU allowance the process detected, in CPUs.
cpu_allowance_source
Where it came from — scheduler/affinity, a cgroup quota, or a fallback.
cpu_budget
The admitted budget after cpu_reserve, in intra-op tokens.
cpu_active_tokens
Tokens currently admitted to resident sessions.
cpu_peak_tokens
The high-water mark since startup.
per-model width
Each model's selected session count and intra-op width, as logged in the startup CPU plan model=… line.

Calibration runs trials at startup, which costs a short burst of CPU before the server accepts requests. A calibrated layout falls back — keeping the explicit width and logging the reason — when the model's demand exceeds the admitted budget, when an explicit intra_op_threads is set, or when the trial cannot validate a candidate.

emb-top

A live terminal dashboard for a running node. It connects over the Redis protocol and pipelines EMB.MODELS, EMB.INFO <model>, EMB.STATS and MONITOR into a single round trip once per second, and renders aggregate request rate and p95 stream charts, a model-activity heatmap, per-model throughput and p50/p95/p99 latency, cache hit ratio with hit/miss/eviction rates, RSS, CPU, connections and a live event ticker. It supports AUTH and TLS, reconnects automatically, and has a headless -once mode for scripts and CI.

emb-stress

emb-top observes a fleet; emb-stress drives one. It takes the same server configuration the fleet was started with — so the models it exercises, their dimensions and their maximum lengths come from the fleet's own contract — and a target that is one host:port or a DNS name, which it expands into one endpoint per address record. It reconciles the configured models against what each node reports, then offers closed-loop load to every node at each level in turn, and reports per endpoint and for the fleet the offered load, the completed requests per second, the p50/p95/p99 latency and the error count. It is a pure RESP client — no model, no ONNX Runtime — so it runs anywhere emb-top does.

Read the two tools together and the pair separates the share a node was offered from the share it served: emb-stress counts what it offered and what was completed, and emb-top observes each node's own share of the fleet. A node offered its equal share that serves less is the node to look at first, and the fleet's sizing line names the resource it is bound on.

08 · Clients

Because the reply is ordinary RESP, any Redis client works unchanged — that is the point of implementing the protocol instead of shipping an SDK. The only decision is whether to decode the bytes yourself or ask for the decimal VALUES envelope.

The emb Ruby gem wraps the same protocol with connection pooling, a proxy API, multi-model support and automatic float32 decoding, and the emb-server gem ships the precompiled binary. Neither is required — they are conveniences over the wire — but the client's three execution modes and the one rule that decides how many commands a scope costs are explained on their own surface.

10 · Laya decision models

Laya is a non-autoregressive decision engine, exported to ONNX and served through the scripted-model path: one checkpoint, a round of typed questions (choice / score / noul), and all answers in one forward pass with calibrated confidence. The preset is scripts/laya.lua; it ports the reference's sequence construction, temperature calibration and answer assembly, and is pinned byte-for-byte against the vendored corpus (see the decision engine plate and the README's Laya section). The plate runs four rounds over the same call: a Snake loop that runs a whole bounded episode in one call — the preset owns the board, the planner and the three typed questions, and the plate animates the frames beside the reference's own probability readout (ported from laya-coreml), a Pac-Man loop on the same contract with its own maze, pellets and ghosts, the email-triage set, and the smallest three-question round.

The three checkpoints

The reference implementations serve three ONNX exports (from codenamev/laya-onnx, the PyTorch weights published as convaiinnovations/laya*); they mount as three model entries, and the reference Router picks per request. Each export lives under its own folder in the repository, so the entry names it with model_subfolder: and the downloader resolves the ONNX and the supporting files under that folder.

english — ModernBERT-large · 421M · context 512
English, general purpose. The default checkpoint.
multilingual — mmBERT-base · 322M · context 1024
100+ languages, roughly twice as fast as english. The router sends a ticket whose script or language the English checkpoint cannot read — Devanagari, Han, Spanish, Arabic — here before the forward pass, because a wrong checkpoint collapses while staying confident.
typed-decisions — ModernBERT-large · 421M · context 1024
Fine-tuned on the typed-decisions workflows: invoice processing, security incidents, customer service, agent-trace observability. Same command surface, its own calibrations.

The decision tree, for anyone

The model reads a question as one sequence, and the sequence is a little tree: the question is the trunk, every option is a branch marked with the model's mask token, and the state — the email, ticket, prompt or JSON — rides at the tail. The template, exactly:

That is one row. A round sends one row per question as a single batch: the email set above is five rows and fifteen markers (6 + 2 + 2 + 3 + 2), and the one forward pass scores every marker at its own position — so the answers all come back together. In a classical decision tree you ask, branch on the answer, and ask again, depth first; Laya's tree is breadth, not depth. No question waits on another's answer, which is why the whole round is one call, one pass, and one reply.

Loops. A decision loop — each step depending on the last — should run where the model runs, not behind a round trip per step. The shipped scripts/snake.lua is the example: it owns the board, a Hamiltonian safety planner and three typed questions, and one EMB.EVSHA ... 1 '{"ticks": 96, "board": null}' returns 96 frames (each with the move probabilities and the shielded result) plus the board to resume from. The page animates the frames locally and prefetches the next episode. The host learns nothing about Snake: it is a task preset, and scripts/pacman.lua is a second one — its own maze, pellets and ghosts, the same one-call contract — so a third task would keep its own rules the same way. Every frame carries the model call's own duration (inference_ms): the host measures emb.run around the session run and returns it as a second value, so the page shows model time, never the request round trip. Pac-Man's planner prefers the shortest path to the nearest pellet and refuses an immediate reversal, so the random-weight checkpoint clears pellets instead of oscillating in place.

Mount an export bundle

A Laya export (from codenamev/laya-onnx: english, multilingual, typed-decisions) mounts like any scripted model — onnx: + tokenizer:, the preset preloaded — and answers over EMB.EVSHA. The export publishes each checkpoint under a folder, so the entry names it with model_subfolder:; the downloader fetches <subfolder>/model.onnx and the supporting files into the configured directory.

warm is optional and changes no answer. Each text in a group is evaluated once through the same scripted path after the model loads, under that group's args, so its reply is already in the reply cache when a client sends the same state and arguments. It does not gate readiness, and it stops as soon as the model has served a client request since the previous text, so a visitor never queues behind the whole declared set. A payload that fails is logged and skipped; a state that was not declared answers exactly as it did before.

The wire contract

One EMB.EVSHA <model> <laya.lua sha1> 1 <state> <questions> [<config>] answers every question. The state is KEYS[1]: a plain string passes through, and a structured state must be Python-style JSON — spaces after every comma and colon ({"from": "a@b", "body": "x"}), because the checkpoints were trained on exactly those strings. ARGV[1] is the questions object; criteria label order is significant (marker order maps to label order), so criteria objects arrive as JSON objects in document order. The checkpoint's envelope — max_len, head_max_len, min_seq, min_markers, temperature (choice/score/noul) and temperature_by_options (buckets 2, 3-5, 6-10, 11+) — belongs to the checkpoint, not the request: it is declared on the model entry's scripts config and read by the preset as emb.script.config, so a client sends only the state and the questions. ARGV[2] remains an optional per-call override. Calibration clamps follow the reference: temperatures outside [0.5, 5.0] clamp, non-numeric values answer with 1.0.

The question schema

choice
One winner: criteria as a label → description object (or an array of labels). The reply is the winning label, the full probability distribution, and confidence.
score
A place on an ordered rubric: criteria as an array of level descriptions, index 0 first. The reply is the expectation over levels, the legend, and confidence.
noul
A yes/no statement: optional true/false descriptions. The reply is the probability of true and confidence as the distance from a coin flip.

The reference implementations ship ready-made question sets as their canonical examples — Laya::Presets.* in the gem and laya.presets.* upstream, byte-identical: triage_questions (intent, urgency, frustration, refund, churn), email_questions (category, spam, phishing, urgency, needs-reply — the set the decision engine plate runs verbatim), guard_questions (jailbreak, injection, sensitive data, harm, topic), moderation_questions, and router_questions. They are JSON the same way any question set is — copy one, or write your own with the schema above.

Reading the answers: confidence, the act/escalate head, the gate

Every answer carries confidence and action.act_probability. Confidence is normalized entropy (1 − H(p) / log k), so it has a true floor: a choice or score sits on the 0–1 scale — 0.0000 is the undecided floor (a uniform distribution, the genuinely ambiguous input), 1.0000 is fully decided; a noul's scale bottoms out at 0.5000 (a coin flip between yes and no), and a single-option question is always 1.0000. act_probability is the act/escalate head's read on the same answer — how strongly the model says “act on this” versus “escalate this” — served as the answer's action field.
