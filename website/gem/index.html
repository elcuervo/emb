Read mode

The Ruby client

One call, one command. The gem is a skin over the Redis protocol with three execution modes on top, and the shape of your call site decides how many commands a scope puts on the wire.

A thin Ruby wrapper over the same Redis commands. It pools, batches and unpacks for you; the wire stays EMB.

THE CLIENT · 3 execution modes · pool 5 · 512 texts per call · 2 gems · v0.4.0

WHAT YOU ARE LOOKING AT

The server answers RESP, and the gem does not change that. What it removes is what you would otherwise write yourself: the unpack('e*') that turns four bytes per number into an array, the registry that remembers one proxy per model, the pool, and the coalescing.

Emb[:minilm]["hello world"] is 384 floats, eager and unremarkable — it sends EMB minilm "hello world" and unpacks the reply. The interesting part is what the same line does under a lazy mode.

01 · YOUR CALL

A model proxy from the client's registry. Eager, it sends; deferred, it hands back a value that has not asked the server for anything yet.

02 · THE POOL

Five persistent connections per instance by default, taken in rotation. Up to five commands run at once; the sixth waits for one to free, and that wait has no timeout of its own.

03 · THE BATCH SCOPE

Where deferred values collect, per thread. The first one used sends the command for the whole scope, and the scope is cleared at the end of the request or job.

04 · THE WIRE

EMB when the scope holds one model, EMB.MULTI when it holds several. The first takes a model and any number of texts; the second takes model/text pairs, so one command can carry several models.

# eager, the default: one command, one vector
Emb[:minilm]["hello world"]
# → [0.0123, -0.0456, …]   — 384 Float, one Array

# VALUES: the same call, asking for the server's self-describing envelope
Emb[:minilm]["hello world", format: :values]
# → { dtype: "FLOAT", shape: [1, 384], values: [0.0123, …] }

THE FOUR WIRE SHAPES

Every way the gem can be told to embed six texts, and the command each one puts on the wire. Read the instrument column downwards: the same six texts in every row, four different counts, and the shape the client sends for each.

  1. lazy: false — the default

    Six calls at the call site become six commands. Each one is its own pass over the model.

    6 commands

  2. lazy: :multi

    Deferred, then coalesced. One model in the scope sends EMB minilm "t1" … "t6"; a scope that mixes models sends EMB.MULTI instead. Chunks are sent one at a time.

    1 command

  3. lazy: :batch

    The same deferral, and the same commands — sent concurrently instead of one after another. Here batch_size: 2 over six texts is three shares of two, in flight at once.

    3 commands, at once

  4. Emb.multi { }

    Explicit and always eager, in every mode: collect pairs, then send one EMB.MULTI minilm "t1" bge "t2" … carrying as many models as you name.

    1 command

THE ONE RULE

In a lazy mode, Emb[:minilm]["text"] sends nothing. It returns a value that asks the server the first time it is used — and that first use pays for every other deferred value in the scope. So the deferral only helps if the values exist before the first one is consumed. That is the whole feature and the whole trap. 

# WRONG — create and consume in the same breath
texts.each { |t| process(Emb[:minilm][t]) }
# six values, each used before the next exists → 6 EMB commands, 6 passes

# RIGHT — create them all, then consume them
loaders = texts.map { |t| Emb[:minilm][t] }
# nothing has been sent yet
loaders.each { |l| process(l) }
# the first use sends ONE EMB minilm "t1" … "t6" for all of them

  1. Interleaved

    Each value is used before the next is created, so each scope holds one text.

    6 commands

  2. Hoisted

    The same six texts, with the calls separated from the uses by one loop.

    1 command

Two consequences follow from the same rule. A value created and never used never embeds at all — it is dropped when the thread's scope ends, which is a leak of nothing. And the scope caches what it resolved, so asking for the same text twice inside one scope costs nothing the second time. Change one call site or turn it on for the whole app with Emb.configure { |c| c.lazy = :batch }; the shape of the call site is the only thing that has to change.

WHEN IT FAILS

A batch that fails fails closed. It raises Emb::ServerError to the code that used the first value, and every deferred item in that batch is removed from the scope — so retrying, or using a sibling from the same failed batch, does not re-send it. The underlying redis error is preserved as cause, and the message names the models, the text count and the attempt count.

WHY NOTHING IS RETRIED BY DEFAULT

EMB.MULTI is not idempotent. A re-send re-runs inference the first send may already have done, so the gem ships reconnect_attempts: 0: one attempt, then a terminal error.

WHY A TIMEOUT IS TERMINAL

A read timeout may have executed server work already. redis-client never re-dispatches one, and the gem counts it as a single attempt rather than a retryable failure.

THE ONE RETRY THAT IS SAFE

A connection refused before the command was written. Given a url array, the router moves that command to the next instance, because a command never sent cannot be duplicated.

WHY THE TIMEOUT IS 10s

redis-client's silent default is 1.0s, and 512 pairs of inference on a shared CPU can outlast it. The gem sets both read and write timeouts explicitly; raise them if you raise batch_size.

Per-pair failure is a different thing and is not an error at all. A pair the server could not embed comes back as a null slot, MGET-style, and that value materializes as nil while its siblings resolve normally. Only a failure of the command itself closes the batch.

THE SCOPE IS PER THREAD

The scope holding deferred values is a thread-local, and it is cleared at the boundary of the work that filled it — so a request cannot inherit another request's cache, and a job cannot leak its scope into the next one. In Rails the railtie wires every boundary it finds, and each can be switched off.

RACK

Middleware inserted into the stack automatically. Cleared after each request, including when the app raises. Opt out with config.emb.middleware = false.

ACTIVEJOB

An around_perform callback on the base class, so every adapter is covered — SolidQueue, Sidekiq, Shoryuken, the test adapters. Opt out with config.emb.job_middleware = false.

SIDEKIQ

A server middleware for plain workers, plus the testing chain when sidekiq/testing is loaded before boot, so fake and inline modes clear per job too.

SHORYUKEN

The same server middleware, registered when Shoryuken is present. Outside Rails, both are a one-line registration into the framework's own chain.

In a threaded server the scope is per thread, so the shape is one coalesced command per thread per flush. That composes with a pool of emb instances rather than competing with it: each instance receives one EMB for a single-model scope and one EMB.MULTI for a mixed one.

TWO GEMS, TWO JOBS

The name is shared and the jobs are not. One gem talks to a server; the other is the server, wrapped so that installing it is one command and no build.

emb — THE CLIENT

Pure Ruby over redis-client, plus batch-loader for the deferral. Nothing to compile, no native extension, and no server of its own.

emb-server — THE DISTRIBUTION

A gemspec around a precompiled binary. gem install emb-server puts emb and emb-top on your PATH; the wrapper picks the binary for your platform and execs it.

The wrapper is thinner than it sounds, and the dependency is the interesting part: the gem does not ship ONNX Runtime. It asks the onnxruntime gem where its shared library is, then runs the server with -ort-lib and that path — so the runtime you install is the runtime the server loads. Platforms are macOS arm64, Linux x86_64 and Linux aarch64, and both gems take their version from the same file as the server, so the client, the binary and the release are one number. 

# the client
gem "emb"

# the server, as a binary you do not build
gem install emb-server
emb -model-repo Xenova/all-MiniLM-L6-v2   # downloads the model, serves on :6379

TWO GEMS · one VERSION · client, binary and server released as the same number

THE EXACT COMMANDS

What the gem sends, spelled out. The argument shapes are the whole contract: a text may repeat, a model may repeat, and VALUES is the one keyword that changes what comes back. 

# EMB — one model, one or more texts, binary reply (the default)
EMB minilm "t1"
EMB minilm "t1" "t2" "t3"

# EMB.MULTI — model/text pairs, mixed models in one call
EMB.MULTI minilm "t1" minilm "t2" bge "t3"

# VALUES — the same two, with the decimal envelope instead of bytes
EMB minilm VALUES "t1"
EMB.MULTI VALUES minilm "t1" bge "t2"

# every reply is float32 little-endian, four bytes a number,
# which is why the gem unpacks with 'e*' and you never see them
# the whole deferred path, in three lines
Emb.configure { |c| c.lazy = :batch }

loaders = texts.map { |t| Emb[:minilm][t] }
loaders.map(&:first)

# → EMB minilm "t1" "t2" "t3" "t4" "t5" "t6"
# one command, one pass, six vectors back in deferral order
