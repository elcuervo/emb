## 2. Admission: bounded and cancellable

- [x] 2.1 Give `permit.Budget` a deadline-aware acquire that returns the release function or a bounded error, keeping the FIFO order for waiters that can be admitted and the existing oversized-alone rule. Verify with deterministic tests: a waiter past its deadline returns the bounded error and is removed from the queue; a released permit admits the next eligible waiter; no waiter is lost or double-counted.
- [x] 2.2 Thread the context from the command handler through the embedding route (`handleEMB` → `embedTexts` → `Pool.Embed`/`Batcher.Embed` → the session wrapper), so a request carries one deadline end to end. Verify a request whose context expires stops waiting and returns an error to the client rather than blocking.
- [x] 2.3 Bound the admission queue and answer the existing busy shape past it, counting each refusal. Verify with deterministic tests that the queue never exceeds its bound, that refusals are counted, and that `PING`/`EMB.READY`/introspection still answer while admission refuses.
- [x] 2.4 Bound and abandon a waiting request: on deadline expiry or cancellation, release the pending admission, leave the queue, and neither run nor count the request. Verify with a test that an expired waiter frees its accounting, that the run counter does not advance for it, and that the caller receives the busy outcome. (A mid-command peer disconnect is not observable through redcon — see the transport note in `design.md` D1 — so the server's own bounded wait is the mechanism; true disconnect cancellation needs a transport change and is recorded there.)
- [x] 2.5 Extend `bench/smoke/verify-gate.sh` so the no-deadline acquire and the unbounded queue are planted regressions. Verify each mutant turns the gate red and names the assertion (`admission-bounded`, `queue-bounded`).

## 3. Admission: fair and work-conserving

- [x] 3.1 Admit a waiter whose width fits current usage even while an earlier, wider waiter is still blocked, reserving one admission unit for narrow waiters when the process budget admits more than one run. Verify with deterministic tests: a wide head blocked at the budget does not prevent a narrow follower from being admitted; total admitted width never exceeds the budget; the reservation never starves the wide waiter indefinitely.
- [x] 3.2 Implement the D4 decision so no run holds the whole budget while other work is pending. Verify with a test that, at a budget of 3 and a single model, two runs are concurrently admissible (or the batch is charged as more than one unit when it occupies more than one window of work), and that the reported width still accounts for the model's share.
- [x] 3.3 If the batch-cost decision is taken, charge a coalesced batch by the work it occupies rather than as one unit, keeping the idle-flush path. Verify a large batch and a small request are concurrently admissible, and that the batch's own latency does not double. (Not taken: task 1.6's measurements selected the D4 form "cap the admitted run's width below the budget" — `policyPoolLayout` splits the share so a second run of the same width fits — so batch-cost charging was rejected as unnecessary; recorded in `design.md` D4 and `bench/repro/pre4-regression/README.md`.)
- [x] 3.4 Plant the FIFO-head regression (a narrow waiter blocked behind a wider head) as a mutant. Verify the gate reports it red and names `admission-fair`.

## 4. Layout parity with pre3

- [x] 4.2 Keep the CPU policy's `allow_spinning: false` default and verify it against the differential rather than changing it: group 1 measured spinning off as faster in both revisions at a fixed layout (pre3 879.0 vs 728.3 req/s at c128, probe p50 138.0 vs 166.9 ms; pre4 405.7 vs 335.2), which overturns the original plan to restore the spinning default.
