# Research: WebGPU shaders (vgpu) vs three.js vs neither for the emb landing page

Scope: read-only research for the decision "should `website/` adopt WebGPU shaders via `vercel-labs/vgpu`, or three.js, or neither?" against the committed constraint (no build step, no dependencies, no CDN, `file://` must work, assets generated by checked-in python tools).

Everything below is cited to a URL. Where a number is my own arithmetic it is labelled `[computed]`. Where I could not verify, it is in *What I could not verify*.

---

## Summary

**Recommendation: neither library, and no WebGPU.** WebGPU is unavailable on `file:` origins in Chrome — the exact browsing mode `website/README.md` promises ("opening index.html over file:// works too") — and caniuse's own data puts WebGPU at 83.99% full / 2.95% partial support, missing *every* Firefox user off Windows, *every* macOS Safari user below Tahoe, *every* iOS user below 26, and Chromium on Linux below 144. A shader therefore has to ship *alongside* a static poster, so it is additive cost, not a replacement for the 837 KB PNG. vgpu is the only one of the three that is honest about its bytes (a CI-enforced 25,600-byte gzip budget for an `effect-only` build), but that 25 KB is a *bundler output*, its published browser entry is 184,905 B raw / 56,412 B gzip untree-shaken with 11 dependencies, and its headless proof needs a 19.2 MB native Dawn binary (~npm + Node 22), all of which break this repo's constraints. The cheapest real win is not a shader at all: it is `cwebp`/`pngquant`, already in the dev shell (`website/AGENTS.md`), applied to the 837 KB matte.

## Findings

### 1. vgpu: what the numbers actually are

1. **"25 KB gzipped" is verifiable and CI-enforced — but it is a bundler output, not the package size.** The `vgpu` package declares `vgpuExperienceBundleBudgetsGzipBytes: { "init-only": 1536, "effect-only": 25600, "triangle-low-level": 28672, "draw-recipe-box": 30208, "full-root": 38912 }` and per-export budgets `{".": 38912, "./scene": 12800, "./core": 3584, "./client": 512, "./three": 2560}`; budgets are "the next 512-byte multiple strictly above the measured size", client entries are a **hard** gate (one byte over fails), tooling entries a soft gate (5% growth tolerated) ([package.json](https://raw.githubusercontent.com/vercel-labs/vgpu/main/packages/vgpu-api/package.json), [CONTRIBUTING.md](https://github.com/vercel-labs/vgpu/blob/main/CONTRIBUTING.md)). So the honest reading is: *an app that imports only `effect` was measured at 25,089–25,600 B gzip*; the root barrel is budgeted up to **38,912 B**, i.e. ~1.5× the headline. The marketing line ("a complete fullscreen effect ships in 25 KB gzipped") is accurate for the fixture it measures and misleading as a description of "add vgpu to my page".
2. **The published package, measured by a third party, is much larger.** bundlephobia reports `vgpu@0.4.1` main = 184,905 B raw / **56,412 B gzip**, dependencyCount 11, with two entries large enough to be listed (`@vgpu/wgsl` ≈106 KB, `@vgpu/core` ≈50.8 KB) ([bundlephobia](https://bundlephobia.com/api/size?package=vgpu@0.4.1)). This is minified-but-not-tree-shaken, so it is an upper bound — but it is the size of the thing you'd have to vendor for a no-build-site, and it is 2.3× the advertised figure.
3. **`@vgpu/wgsl` does not strictly require a bundler; the browser entry still needs a module resolver.** `effect(gpu, source)` and `draw(gpu, { shader })` accept WGSL as a plain string, and `resolveShader()` resolves a `.wgsl` entry file and its imports without webpack/Vite/Turbopack — but the documented recipe is a **Node** script (reads from disk, writes a PNG via pngjs) ([no-bundler guide](https://raw.githubusercontent.com/vercel-labs/vgpu/main/docs/topics/no-bundler.docs.md)). For the browser: `vgpu/dist/index.js` has relative imports plus exactly one bare specifier, `@vgpu/wgsl` (`import { isShaderFunctionExport } from "@vgpu/wgsl"`), and `@vgpu/wgsl/dist/index.js` is 143 B of relative re-exports (`compile`, `isShaderFunctionExport`) [fetched from unpkg]. So a `<script type="module">` page *can* load vgpu with a vendored tree + an import map naming `@vgpu/wgsl` — but the `.wgsl`-in-its-own-file workflow needs the loader, and the loader is a bundler plugin.
4. **"Unused declarations are pruned" means WGSL declaration-level dead-code elimination at build time, not JS tree-shaking.** The evidence is a unit test named `"unused imported @vgpu/wgsl-std declarations are removed"` which resolves a shader importing `srgbToLinear3` from `@vgpu/wgsl-std/color` and asserts unused declarations are gone ([distribution-dce test](https://github.com/vercel-labs/vgpu/blob/1905a0cb/packages/wgsl/tests/declaration-dce.test.ts)). It is a real optimisation and it is why the std/utility library (e.g. noise) doesn't all ship — but it applies to shader text produced by the resolver, i.e. only in a build.
5. **`npx vgpu check <file.wgsl>` validates and reflects: JSON with binding names, groups, entry points, non-zero exit on error.** "It validates without running and prints the shader's reflection as JSON — binding names, groups, entry points — so you can confirm the names you will pass to `set()`. It exits non-zero with the validation errors when the shader is wrong." ([shader workflow](https://vgpu.sh/docs/guides/shader-workflow), [CLI](https://vgpu.sh/docs/cli)). This is genuine value raw WebGPU has none of.
6. **Headless rendering = Dawn, i.e. a native binary, ~19 MB on macOS, and a broken install path on x64 Linux.** `vgpu/node` renders through Dawn; on Linux it resolves a stock prebuild, falls back to a portable build downloaded from GitHub Releases with a pinned SHA-256, and `npx vgpu install-software-renderer` provides a CPU (lavapipe) fallback ([Node docs](https://vgpu.sh/docs/get-started/node)). Platform reality: the upstream `webgpu@0.4.0` (Dawn) release assets are `darwin-universal.dawn.node` **19.2 MB**, `linux-arm64` 15.7 MB, `linux-x64` 17.8 MB, `win32-x64` 10.5 MB ([release page](https://github.com/dawn-gpu/node-webgpu/releases/tag/v0.4.0)) — so **macOS arm64 headless works**, via a 19.2 MB binary. vgpu's *own* portable prebuild is linux-arm64-only: `npx vgpu install-dawn` exits 1 with `VGPU-NODE-PREBUILD-MISSING: unsupported platform linux/x64` on x64 Linux, and the maintainers' own issue says that failure is misleading because the stock `webgpu` path covers it ([issue #262](https://github.com/vercel-labs/vgpu/issues/262)). Also: `@vgpu/adapter-node` runs a `postinstall` script ([package.json](https://raw.githubusercontent.com/vercel-labs/vgpu/main/packages/adapter-node/package.json)) — relevant to nix/pnpm sandboxes.
7. **When WebGPU is unavailable, vgpu throws — there is no fallback.** `init()` **throws `VGPU-RING1-UNSUPPORTED`** when WebGPU is unavailable, when `requestAdapter()` returns `null`, or when an entrypoint lacks an adapter factory; the remedy is `vgpu/mock` (tests) or `vgpu/node` ([init reference](https://vgpu.sh/docs/reference/vgpu/init)). Compare three.js, which does ship a WebGL2 fallback entry loaded on demand ([PR #34334](https://github.com/mrdoob/three.js/pull/34334)). Consequence for emb: a shader hero needs a hand-written probe (`if (!navigator.gpu) …`) plus the static poster you already have.

Skeptical note on vgpu: it is at **0.4.1**, publishes 7 fixed-version packages with an elaborate release/promotion policy, and the marketing surfaces ("one public API surface across the browser, headless Node (`vgpu/node`, Dawn-backed), and a deterministic mock (`vgpu/mock`) built for tests and CI") [README] are accurate but the *CI* story is where it strains — headless verification requires a 19.2 MB native binary, a `postinstall`, and (on x64 Linux) an `install-dawn` command that visibly fails while actually working. Its real home is a bundler-based, always-HTTPS Next.js/Vercel app, which is the opposite of this site.

### 2. WebGPU availability in 2026, with the actual numbers

8. **caniuse's current data: 83.99% full support, 2.95% partial** (`usage_perc_y` 83.99, `usage_perc_a` 2.95 in the raw feature JSON, fetched today) ([webgpu.json](https://raw.githubusercontent.com/Fyrd/caniuse/main/features-json/webgpu.json)).
9. **The gaps are specific and non-trivial** (same source, `notes_by_num`):
   - **Safari desktop: `a` (partial) from 26.0 onward**, note #7: "Partial support refers to only being enabled by default on **macOS 26 Tahoe or later**." iOS Safari 26.0+ is full `y`. So desktop Safari below Tahoe has none, while iOS 26 is fine.
   - **Firefox: 141–144 = `a`**, note #6 "Only enabled by default on **Windows**"; **145+ = `a`**, note #8 "Only enabled by default on Windows as well as **macOS 26 Tahoe or later on Apple Silicon**." Firefox **Android** 153 is `n d #1` (flag only). Firefox on Linux and Intel Macs: not enabled.
   - **Chrome/Edge 113+ = `y` but note #5 "Not enabled on Linux by default"**; from Chrome 144, note #9 "Support on Linux depends on hardware and drivers." Chrome 144 is 2026-01-13 ([webstatus.dev](https://webstatus.dev/features/webgpu)).
   - Samsung Internet 24+ and Opera 99+ are `y` (Opera also with the Linux caveat).
10. **Traffic share of the gap** (browser shares, August 2026: Chrome 69.39%, Safari 15.83%, Edge 5.36%, Firefox 2.98%, Samsung 2.01%, Opera 1.94%) ([StatCounter](https://gs.statcounter.com/browser-market-share)), combined with version data:
   - All Firefox users are ≤ a partial: 2.98% of browser share, minus the Windows-only subset that works ([StatCounter](https://gs.statcounter.com/browser-market-share), [caniuse](https://raw.githubusercontent.com/Fyrd/caniuse/main/features-json/webgpu.json)).
   - iOS below 26 ≈ 14.5% of iOS traffic (iOS 18.7 10.36%, iOS 16.7 1.84%, plus the long tail) ([StatCounter iOS versions](https://gs.statcounter.com/os-version-market-share/ios)) → no WebGPU.
   - macOS below Tahoe ≈ 14% of tracked macOS installs (Tahoe 86.0% in the week of 27 July 2026 per TelemetryDeck) ([macOS distribution write-up](https://www.aboutchromebooks.com/macos-version-distribution-statistics/), [TelemetryDeck](https://telemetrydeck.com/survey/apple/macOS/versions/)) → desktop Safari on those machines has none.
   - Linux desktop Chromium below 144, plus driver-dependent support.
   `[computed]` A defensible planning figure is **~80–84% of visitors can run it, and ~16–20% cannot** — and on `file://` the answer is 0%.
11. **The "capability" number is inflated by Android/Chrome; a secondary tracker puts Linux at 16.61% support vs Android 70.83%, macOS 89.27%, Windows 86.68%, iOS 84.51%** ([Web3D Survey](https://web3dsurvey.com/webgpu) — secondary aggregator, treat as indicative). A widely-shared 2026 write-up claims only **0.004% of Chrome page loads actually submit work to a GPU**, i.e. a ~21,000× gap between "can" and "does" ([enterno.io](https://enterno.io/en/s/research-webgpu-adoption-browsers-2026)). I could **not** trace that last figure to a Chrome UseCounter or `chromestatus.com` row (the metrics UI is JS-rendered and unfetchable) — see *What I could not verify*. The direction (WebGPU usage ≪ availability) is consistent with vendor intent posts such as Mozilla's "shipped to release on Windows in Firefox 141 without serious incident" ([intent to ship](https://groups.google.com/a/mozilla.org/g/dev-platform/c/4m_SnGAGkEU/)), but the exact 0.004% is unverified.
12. **WebGPU is also blunter than it looks in the same browser.** Chrome 146 (Feb 2026) added an opt-in "compatibility mode" on OpenGL ES 3.1 precisely because "many users have older hardware that does not support [Vulkan/Metal/D3D12]" ([Chrome 146](https://developer.chrome.com/blog/new-in-webgpu-146)) — i.e. even a `navigator.gpu`-positive visitor may not have a usable adapter.

### 3. The raw-WebGPU alternative

13. **Lines and bytes:** the canonical single-pass fullscreen fragment shader (no library, no vertex buffer, `@builtin(vertex_index)` quad, one `resolution` uniform, `requestAnimationFrame` loop) is **3,123 B of source including WGSL and comments** ([gist, "simple example of rendering to the whole screen with a fragment shader in WebGPU"](https://gist.github.com/Ella-Hoeppner/be92d7fffa83b226a7a62088886e98e0)); a fully-commented triangle is 6,330 B ([toji/hello-triangle-webgpu](https://github.com/toji/hello-triangle-webgpu/blob/main/index.html)). `[computed]` comment-stripped, minified and gzipped that is roughly **0.6–1.2 KB**, i.e. **~1/40th of the vgpu effect-only budget** and **~1/150th of three's tree-shaken minimum**. Independent confirmation of the shape of these numbers: "Raw WebGL for a single full-screen quad is roughly forty lines" ([21st.dev](https://21st.dev/blog/react-animated-background-components)).
14. **What you lose by hand-rolling** (each maps to a vgpu/vendor feature with a doc URL): `vgpu check`-style WGSL validation and reflection-as-JSON ([shader workflow](https://vgpu.sh/docs/guides/shader-workflow)); uniform/pipeline binding by name through `set({params:{…}})` instead of manual `createBindGroup` + byte offsets ([init reference](https://vgpu.sh/docs/reference/vgpu/init), [gist](https://gist.github.com/Ella-Hoeppner/be92d7fffa83b226a7a62088886e98e0)); structured errors (`VGPU-FEATURE-UNSUPPORTED`, `VGPU-NODE-PREBUILD-MISSING`) versus raw `TypeError`/null ([init](https://vgpu.sh/docs/reference/vgpu/init), [Node](https://vgpu.sh/docs/get-started/node)); and the headless render test — but note **headless needs the same Dawn binary either way** ([release assets](https://github.com/dawn-gpu/node-webgpu/releases/tag/v0.4.0)), so vgpu's CI advantage over raw is tooling convenience, not new capability.
15. **A hand-rolled shader still fails the repo's constraints.** Two independent blockers: (a) **`file://`** — Chrome's own troubleshooting says "WebGPU is accessible only to secure contexts. If you serve your code over an insecure protocol (for example, `http:`, `file:`), either use the secure `https:` protocol or … serve locally on `http://localhost`" ([Chrome](https://developer.chrome.com/docs/web-platform/webgpu/troubleshooting-tips)); the spec marks the interfaces `[SecureContext]` ([W3C WebGPU](https://www.w3.org/TR/webgpu/), [MDN](https://developer.mozilla.org/en-US/docs/Web/API/WebGPU_API)); (b) **module scripts don't load over `file://`** — "if you try to load the HTML file locally (i.e. with a `file://` URL), you'll run into CORS errors due to JavaScript module security requirements" ([MDN JavaScript modules](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Modules)), which forces the glue to be an **inline** script if you want any JS at all over `file://`. Note WebGL2 has no such secure-context gate (95.73% y, [caniuse](https://raw.githubusercontent.com/Fyrd/caniuse/main/features-json/webgl2.json)) — so if a shader is ever wanted, **WebGPU is the ~12-point-narrower bet, not the wider one**.

### 4. three.js

16. **Sizes:** `three@0.184.0` full min build is **724,189 B raw / 181,947 B gzip** ([bundlephobia](https://bundlephobia.com/api/size?package=three@0.184.0)). A tree-shaken minimal build ("renderer, camera, empty scene, and dependencies") was measured at **418.7 kB / 102 kB gzip** ([PR #25778](https://github.com/mrdoob/three.js/pull/25778)); the r184-era tree-shaken WebGPU build measures **680,858 B / 184,453 B gzip**, with the WebGL2 fallback as a separate on-demand chunk of **97,106 B / 26,307 B gzip** ([PR #34334](https://github.com/mrdoob/three.js/pull/34334)). The code-split (`build/three.core.js`, one shared core across WebGL/WebGPU entrypoints) landed in **PR #29404** ([codesplit WebGL/WebGPU entrypoints](https://github.com/mrdoob/three.js/pull/29404)); the tree-shaking groundwork for nodes/materials in [#29187](https://github.com/mrdoob/three.js/pull/29187) and [#28328](https://github.com/mrdoob/three.js/pull/28328).
17. **`three/webgpu` is not needed for a fullscreen quad — and is not the small path either.** `WebGPURenderer` routes through the nodes/TSL system and its tree-shaken build is ~184 KB gz ([PR #34334](https://github.com/mrdoob/three.js/pull/34334)); the WebGL `WebGLRenderer` on the code-split core is the smaller of the two (~102 kB gz minimum, [PR #25778](https://github.com/mrdoob/three.js/pull/25778)). Either way you are paying for a scene graph, a camera, materials and a render loop to draw two triangles.
18. **Is three ever smaller than raw WebGPU?** For a single fullscreen quad, no: the honest comparison is ~1 KB of glue vs ≥102 KB gz of library, and the ecosystem's own advice is "reach for three when you have a scene, not a rectangle" ([21st.dev](https://21st.dev/blog/react-animated-background-components)). Where three *does* win: it is the only one of the three with a real fallback path (dynamic WebGL2 fallback chunk, [PR #34334](https://github.com/mrdoob/three.js/pull/34334)) — but that widens coverage to WebGL2's 95.73%, still not `file://`-proof and still 100+ KB.

### 5. Precedent: is a hero shader a differentiator or a cliché in 2026?

19. **Cliché, and now vendor-manufactured.** Vercel's own `vgpu.sh` landing page ships a WebGPU "prism" hero built with vgpu, documented in a Codrops case study: "One week before launch, the vgpu landing page was still missing its hero…" ([Codrops, Sept 2026](https://tympanus.net/codrops/2026/09/03/from-rays-to-meshes-building-vercels-prism-with-vgpu/)). Vercel also maintains template/lab shader heroes ([vercel-labs/nextjs-nights-shader](https://github.com/vercel-labs/nextjs-nights-shader)) and published WebGL conference-experience posts ([vercel.com blog](https://vercel.com/blog/building-an-interactive-webgl-experience-in-next-js)). Note the *shape* of the precedent: all of these are Next.js apps with bundlers, npm and HTTPS — none is a no-build static page.
20. **Supply of shader heroes is measurable.** Of 155 public "background" components catalogued by 21st.dev, **30 use WebGL and 15 of those pull in three**, and **67 run a continuous frame loop** ([21st.dev](https://21st.dev/blog/react-animated-background-components)); component marketplaces sell ready-made "Shader Hero"/"Shader Playground" heroes ([crazygl](https://crazygl.com/hero/shader-playground-hero), [select.codes](https://select.codes/components/shaders-hero-section)). A hero shader is a catalogue item, not a signature.
21. **The accessibility rule is normative, not a preference.** WCAG 2.2 SC 2.2.2 (Pause, Stop, Hide, Level A) requires a mechanism to pause/stop/hide any automatically-starting motion that lasts >5 s and runs in parallel with content ([W3C Understanding 2.2.2](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide)); `prefers-reduced-motion` is an accepted sufficient technique for author-controlled motion ([C39](https://www.w3.org/WAI/WCAG22/Techniques/css/C39), [SCR40](https://www.w3.org/WAI/WCAG22/Techniques/client-side-script/SCR40)) with an open clarification about whether the media query alone satisfies 2.2.2 ([w3c/wcag#4319](https://github.com/w3c/wcag/issues/4319), [#3766](https://github.com/w3c/wcag/issues/3766)). `DESIGN.md` § Accessibility already mandates honouring `prefers-reduced-motion` (and requires the signal line to appear immediately, diagram layers not to animate) — an always-on shader would be the one element that must add a *second* accessibility story (pause control + a static frame), and the catalogue data shows how rarely that happens: **5 of 155 components check `prefers-reduced-motion`, 5 have an `IntersectionObserver`** ([21st.dev](https://21st.dev/blog/react-animated-background-components)).
22. **Energy/battery, with measurements.** On an M1 MacBook (powermetrics, median of 3×10 s): idle page ≈25 mW, video 50–150 mW, CSS/SVG animation 100–500 mW, **WebGL 200–2 000 mW**, and that test shader is described as "near the minimum energy draw you'd see in a stylised shader background used in a live site, with more complicated effects taking up potentially several Watts more GPU power" ([Torchbox](https://torchbox.com/wagtail-cms-services/blog/how-much-power-do-web-assets-use/)). Cost scales with pixels × frames: a 1440×900 canvas at DPR 2 is **5.2 M pixels/frame, 311 M/s**; a mid-range phone at 390×844 DPR 3 is **2.9 M fragments/frame, 178 M/s**, and "four octaves of noise per fragment is where those devices give up, and they do not give up by dropping frames: they thermally throttle" ([21st.dev](https://21st.dev/blog/react-animated-background-components)). `DESIGN.md`'s mountain treatment (grayscale + halftone + dither) is exactly the "four octaves of fbm" shape.
23. **I did not audit fly.io / modal.com / neon.tech DOMs** (no browser-automation tool available in this run) — see *What I could not verify*. The Vercel precedent plus the component-marketplace supply is the evidence I do have.

### 6. Could a shader *replace* the 837 KB matte?

24. **The technique is well-trodden and cheap to specify**: ridged/2D multifractal value noise for the ridge silhouette (a ~30-line pure WGSL function, e.g. [`ridged2.wgsl`](https://github.com/vista-art/fragmentcolor/blob/main/docs/website/public/shaders/noise/ridged2.wgsl)) plus ordered-dither thresholding with a Bayer matrix for the 1-bit look ([lygia `color/dither/bayer.wgsl`](https://github.com/patriciogonzalezvivo/lygia/blob/main/color/dither/bayer.wgsl), [debanding shader using a 4×4 Bayer matrix](https://github.com/daika7ana/Anime4K-WebExtension-Plus/blob/main/src/shaders/debanding.wgsl), background on the technique in [Codrops](https://tympanus.net/codrops/2025/06/04/building-a-real-time-dithering-shader/)). Resolution independence is real: the ridge is evaluated at device-pixel resolution, so there is no re-export at 2×/3× and no fixed 2172×724 raster to scale.
25. **But the costs are the ones this repo measures carefully.** (a) *Float non-determinism*: identical WGSL produces different pixels across vendors/drivers, and fbm/ridged noise amplifies small differences near the dither threshold — there is no `pngquant`-style reproducible output, and the current asset pipeline is byte-deterministic python (`website/AGENTS.md`: pillow/numpy "for image measurement"). (b) *Motion/thermal budget on phones*: four-octave noise per fragment is the documented throttle point ([21st.dev](https://21st.dev/blog/react-animated-background-components)); a static (one-frame) render avoids the battery problem but then you have paid for a shader to make a still image you could have rasterised once. (c) *Art direction*: the shipped matte is a photographic-derived cut-out carrying 11 measured correction passes, and the orange route polyline was traced from a different source image than the shipped art — a procedural ridge cannot reproduce either, so the route would have to be re-traced against the new silhouette, and the "print texture / halftone" quality would become a tunable rather than an authored asset. (d) `DESIGN.md` already assigns the route overlay and the silhouette work to **SVG** ("SVG is ideal for: pipeline lines / signal path / exploded architecture / crosshairs / icons / **mountain path overlay**", ≈L1351) — a traced ridge as SVG paths + a tiled dither pattern gets the same resolution independence and the same 1-bit language with **zero** JS, and `DESIGN.md` § Texture already asks for "subtle paper grain / very faint noise / halftone imagery" as a CSS/SVG-level effect. So: **the resolution-independent argument does not require WebGPU at all.**

### 7. Replacing the 837 KB PNG without a shader (the cheapest win)

26. **The asset is already well compressed, so pngquant's headline number will not hold.** `[computed]` 2172 × 724 = 1,572,528 px; 837 KiB ÷ 1,572,528 px = **0.545 B/px ≈ 4.36 bits/px** (≈4.26 bpp if "837 KB" is decimal). pngquant's claims — "often as much as 70%" ([pngquant.org](https://pngquant.org/)) and "often 60-80% smaller than 24/32-bit PNG files" ([kornelski/pngquant](https://github.com/kornelski/pngquant)) — use a 24/32-bit baseline; this file is already at ~13–27% of a raw 32/16-bit raster, so those percentages are not attainable. pngquant's own head-to-head example is the honest anchor: **210 KB → 195 KB (117 KB after optimisation), "almost 40% smaller file size after optimization"** vs Photoshop's palette ([pngquant vs Photoshop](https://pngquant.org/vsphotoshop.html)), and an independent walkthrough shows "Compressed size: 193 KB (73% reduction)" from a much larger source ([Ryan Harrison](https://ryanharrison.co.uk/2017/10/15/png-optimisation.html)). `[estimate, not measured]` **Realistic pngquant + optipng for this asset: ~835 KB → ~300–550 KB (30–60% off).**
27. **A single WebP is likely the bigger win, and it is already in the toolchain.** WebP covers **96.09% full support / 0.09% partial** ([caniuse raw JSON](https://raw.githubusercontent.com/Fyrd/caniuse/main/features-json/webp.json)); iOS Safari has been `y` since 14.0, so a `<picture>` fallback is optional. Google's own study: lossless WebP is **23% better than ZopfliPNG and 42% better than libpng**, with the caveat that "WebP offers *lossy* compression with alpha support, providing further opportunities" ([Lossless and Transparency Encoding in WebP](https://developers.google.com/speed/webp/docs/webp_lossless_alpha_study)); the alpha gallery pairs PNG/WebP-lossless/WebP-lossy-with-alpha side by side ([gallery](https://developers.google.com/speed/webp/gallery2)); and for exactly this content type — "a photographic PNG with a transparency" — lossy WebP is reported "at least 25% smaller, sometimes significantly better" ([WebAware](https://snippets.webaware.com.au/snippets/photographic-png-transparency-lossy-webp/)). `[estimate, not measured]` **Lossy WebP with alpha at q≈80 over an already-posterised/halftoned matte: plausibly 150–350 KB**, and the DESIGN.md treatment (grayscale, `contrast(1.4)`, halftone/dither) masks lossy artefacts that would be visible on a smooth photographic gradient. `cwebp`, `imagemagick`, `pngquant`, `optipng` are all in the dev shell ([website/AGENTS.md](./AGENTS.md)), so this is a checked-in-tool change, not a new dependency.
28. **Asset-diet math for the page as a whole** `[computed]`: fonts 145 KB + PNG 837 KB + JS 19.5 KB ≈ 1.00 MB. Re-encoding the matte to ~250 KB and dropping nothing else takes the page to ≈415 KB with **no new bytes of JS at all** — a bigger improvement than any of the three shader options could deliver, since all of them are additive.

## Gaps / what I could not verify

1. **I could not measure anything.** This run had no shell, so `pngquant`, `cwebp`, `optipng`, `gzip -9`, and any bundle-size experiment were impossible. Every image/JS size in §7 and the raw/three/vgpu byte comparisons are either vendor-published or my arithmetic on the stated asset sizes — labelled `[computed]` / `[estimate, not measured]`.
2. **The site's own files are not in this worktree.** `website/` here contains only `AGENTS.md`, `README.md` and `DESIGN.md`; `index.html`, `main.js`, `tools/gen-isometric.py`, `tools/gen-terrain-matte.py` and `assets/img/terrain-matte.png` all returned ENOENT. So the brief's "837 KB PNG (2172×724), 145 KB of woff2, 19.5 KB main.js" are taken on trust, not verified against disk.
3. **The 0.004%-of-page-loads WebGPU usage figure is unverified.** `chromestatus.com/metrics/feature/timeline/popularity/*` is JS-rendered and unfetchable here; caniuse's numbers are the only support figures I could confirm from a primary. If the argument "nobody uses WebGPU" matters, get the UseCounter from the Chrome Platform Status UI directly.
4. **No DOM audit of comparable landing pages.** I have no browser automation in this run, so I cannot state that fly.io / modal.com / neon.tech do or do not use canvas/WebGL. The precedent finding rests on Vercel's documented vgpu hero and on marketplace supply counts.
5. **Headless-Chrome WebGPU on this repo's tooling is untested.** `agent-browser` documents a `--webgpu` preset and macOS presets exist, but I could not confirm Chrome-for-Testing-as-installed-here (`just website-browser`) acquires a Metal adapter for a WebGPU screenshot, or what flags it needs on this machine. This is the single most useful 10-minute experiment to run before any shader decision: `agent-browser --webgpu …` against a two-line WebGPU page and check the pixels aren't black.
6. **vgpu's actual measured `effect-only` size is only bounded, not known** (25,089–25,600 B gz by the 512-byte rounding rule). If the exact figure matters: `pnpm bundle-check` in a vgpu checkout.
7. **WebP/AVIF encode settings are not chosen.** Without running `cwebp` I cannot pick q/`-alpha_q`/`-preset`, nor confirm whether the dev shell's imagemagick has libheif for AVIF (AVIF support tables were not pulled).
8. **Whether WebGL/WebGL2 actually runs from `file://`** in Chrome 2026 is asserted from the absence of a `[SecureContext]` marker on the WebGL interface and the presence of one on WebGPU ([W3C WebGPU](https://www.w3.org/TR/webgpu/)) — I found no vendor doc stating `file://` behaviour for WebGL explicitly. Verify by opening a tiny WebGL page over `file://` before relying on it.
