# Design

See `proposal.md` for motivation. This covers how the contract is produced, held stable, and consumed.

## Context

- Routes are registered one by one on a `redcon.ServeMux` (`internal/server/server.go:394-415`). The mux exposes no route enumeration, so "the artifact covers the server" cannot be checked by walking it; a Go-side table is required for either direction of that check.
- `EMB.HELP` builds a prose body in `handleHELP` (`server.go:1940`). `docs/commands.md` is a hand-written table; `website/docs/index.html` repeats a subset. Four spot tests assert individual commands appear in help.
- The gem sends 17 distinct command literals from `batch_dispatch.rb`, `image_command.rb`, `multi.rb`, `commands.rb`, `client.rb`; there is no inventory, which is how `EMB.IMGMULTI OUTPUTS` went missing while every test passed.
- The repo already has the generate/check idiom: `just website-presets` writes, `just website-presets-check` fails on drift, CI runs the `--check` form. `VERSION` is the single version source.
- Redis's model (authoring JSON per command → generated `commands.def` + docs JSON, third parties read `COMMAND DOCS`, `reply_schema` as JSON Schema) is the reference. emb borrows the contract idea, not the codegen chain or the nested argument tree.

## Goals / Non-Goals

**Goals:**
- One writer: the Go declaration. Every other representation derives from it or is tested against it.
- A checked-in artifact a client can pin and diff, with a CI gate that makes drift impossible to merge.
- Machine-checked names and keywords; the two image reply shapes expressed as JSON Schema.
- A closed flag vocabulary that classifies commands without carrying deployment policy.

**Non-Goals:**
- A Redis-style `oneof`/`block` argument tree, or codegen into client libraries.
- Reply schemas beyond the image commands; `EMB.HELP` generation from the table; `docs/commands.md` generation.
- A runtime introspection command, and deriving the sandbox allowlist from flags.
- OpenAPI or CEL, per the exploration.

## Decisions

### Declaration lives in Go, in its own dependency-free package

The table lives in `internal/contract` — no imports beyond the standard library — and `internal/server` imports it to register routes (`s.route(mux, contract.Embed, s.handleEMB)`). A test in `internal/server` asserts every mux-registered name has exactly one declaration and vice versa.

- *Why its own package:* `internal/server` imports `internal/registry`, which links ONNX through CGo. A generator importing the server would need the native runtime just to print JSON, and the CI gate would inherit that. A stdlib-only table keeps `cmd/emb-commands` buildable with `CGO_ENABLED=0`.
- *Alternative:* a hand-authored YAML/JSON consumed by Go. Rejected — the coverage test needs a Go-side list regardless, so this option pays for two writers and still needs the same test.
- *Alternative:* derive entries by reflecting over handler names. Rejected: handler names do not spell wire names, and reflect buys nothing the table doesn't.

### `commands.json` at the repository root

Sits beside `VERSION`; `llms.txt` already advertises raw-GitHub documentation paths, so clients pin a URL rather than discovering a path. Generated by `cmd/emb-commands` run from `just commands-gen`; `just commands-check` writes to a temp path and diffs, exiting non-zero with the differing command names.

- *Alternative:* `docs/commands.json` — equally workable, but docs tooling treats `docs/` as prose, and the artifact is an API contract.
- *Alternative:* generate at release time only. Rejected: drift would surface after tagging.

### Entries carry a flat keyword list and an arity shape

`keywords` is an ordered list of the literal tokens a command accepts; `arity` is `{min, tail}` where `tail` describes repetition (`none`, `pairs`, `even-pairs`, `variadic`). `EMB.SCRIPT` stays one entry whose keywords are `LOAD|EXISTS|FLUSH`, because a client's validation problem is "is this token allowed here", not "render a syntax tree".

- *Alternative:* Redis's argument tree. Rejected: emb has one subcommand family and no nested blocks; a tree would need a validator to be worth its bytes, and the tree's value (syntax rendering) is served by the existing `grammar` string.

### `reply_schema` is narrow and describes logical values

Only `EMB.IMG` and `EMB.IMGMULTI` carry `reply_schema` (JSON Schema draft 2020-12), stating the logical shape — a keyed map for one image, an array of keyed maps with nullable slots for several. A sibling `wire_notes` string records the encodings the schema does not: RESP2 flat alternating pairs versus RESP3 map, and how `VALUES` envelopes replace bulks.

- *Alternative:* schemas for the whole surface. Rejected: Redis calls its own reply schemas immature after a decade; only the two positional commands have shapes a client can get wrong silently.
- *Alternative:* no schemas. Rejected: both client bugs this week lived here, and a schema is the only form a gem spec can mechanically diff.

### Flags are a closed vocabulary, deployments decide

`flags` draws from: `inference`, `introspection`, `writes-state`, `changes-config`, `exposes-traffic`, `terminates-server`. Flags classify; they never encode a deployment's policy (the sandbox's `surface` string stays in `website/repl/allowlist.go`).

- *Alternative:* CEL policies. Rejected for now: the only current policy is ~40 lines of readable Go, and CEL would add a parser and a dependency to express `!has(flags.admin)`.
- *Alternative:* free-text flags. Rejected: unverifiable.

### The gem vendors the artifact and validates without hand lists

`gems/emb/lib/emb/commands.json` is a copy refreshed by `rake commands:sync` (already shipped by `lib/**/*`). Three specs: every command literal found in `lib/` is declared; every keyword a builder emits for a command is declared for that command (checked by running the builders against a recording client and intersecting emitted tokens with the declaration); the vendored bytes equal the repository artifact when the repository file is reachable (skipped for a standalone gem install).

- *Alternative:* fetch the contract at gem build time from a URL. Rejected: offline gem builds, and a network dependency in `gem build`.
- *Alternative:* runtime validation on connect. Deferred: "validate their builds" is a build-time property; a live check is a separate feature with its own failure mode.

### The artifact carries no server version

`commands.json` holds `contract` (format version, `1`) and `commands`. It omits the server version deliberately: `VERSION` is the release version, and embedding it would make `commands-check` fail on every release for a one-token diff. Clients pin the contract by git tag or gem version instead.

- *Alternative:* embed `server_version` and let the release bump regenerate. Rejected: a gate that fails on an unrelated bump trains people to regenerate without reading.

## Risks / Trade-offs

- [The docs table and `EMB.HELP` prose stay hand-written; only their command *names* are checked] → The artifact is authoritative and linked from both; keyword drift in prose is a docs bug, not a contract bug. Mitigation if it recurs: generate the markdown table too.
- [`commands-check` fails on any declared change, including one that only reorders keywords] → Intended: the artifact is the diff review surface. Keep entries sorted by name so the churn is local.
- [Flag vocabulary will attract deployment-specific additions] → Closed list reviewed in the spec delta; additions are a spec change, not an entry tweak.
- [Gem keyword validation can only see tokens the specs actually exercise] → Accept: the builders' token sets are the union of what specs drive, and an unexercised keyword is an untested builder path either way.
- [Vendoring creates a second copy that can go stale] → The equality spec fails on it, and `rake commands:sync` is the fix.

## Migration Plan

Additive: no wire behavior changes, no config keys, no dependency. Land the table and artifact first (server tests green), then the gem copy and specs. Rollback is deleting `commands.json`, the two `just` targets, and the gem copy — nothing else references them.

## Open Questions

- Whether `EMB.HELP JSON` should later serve this contract at runtime, so a client can validate against a live server. Deferrable: no spec change, one handler.
- Whether the sandbox `surface` string should be generated from flags plus `sandbox.yaml`. Deferrable; the flags field is the prerequisite either way.
